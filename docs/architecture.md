# Architecture

## Overview

```
Frontend (public/)
      ↓
Express Server (server.js)
      ↓
Demo Session Manager
      ↓
Risk Simulation
      ↓
Identity Impersonation
```

## Components

### Frontend (`public/`)
Plain HTML/CSS/JS pages. No build step, no frameworks. Each page calls the
backend's JSON API using `fetch()`.

- `index.html` — landing page
- `login.html` — login form, demo credentials shown inline
- `dashboard.html` — shows the current user's fake session details
- `profile.html` — shows the profile resolved from the active session
- `attack-demo.html` — the two-panel (User A / User B) hijacking simulation
- `security-result.html` — standalone risk score + event timeline view

### Backend (`server.js`)
An Express app exposing a small JSON API (see below). All state is kept
in-memory for the lifetime of the server process:

- `users` — loaded once from `data/users.json` (fixed demo accounts)
- `sessions` — a dictionary of `sessionId -> session record`
- `browserContext` — two slots, `A` and `B`, each simulating a distinct
  browser. This is what lets the attack-demo page show a session created
  for Alice being reused by "Bob's browser."
- `events` — an append-only list used to render the security timeline
- `currentRisk()` — derives a 0–100 risk score from the current state

### Data (`data/`)
- `users.json` — the two fixed demo accounts (plaintext demo passwords —
  intentionally simple since this is a local teaching tool, not a real
  authentication system)
- `sessions.json` — present for structural completeness; the running app
  keeps sessions in memory and does not persist them across restarts

## API Surface

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/login` | Authenticate a demo user, create a fake session |
| GET | `/api/session/current` | Resolve the active session (by id or browser slot) |
| GET | `/api/session/:id` | Look up a specific session record |
| GET | `/api/session/browser/:slot` | Convenience lookup for the A/B attack-demo panels |
| POST | `/api/session/simulate-compromise` | Mark a session as `SIMULATED_COMPROMISED` |
| POST | `/api/session/inject-demo` | Point a browser slot at another session's id |
| POST | `/api/session/revoke` | Invalidate a session |
| POST | `/api/demo/reset` | Clear all sessions/events/risk back to the start |
| GET | `/api/security/events` | Return the event timeline |
| GET | `/api/security/risk` | Return the current risk score |

## Why this is safe

- Session identifiers are application-level strings generated by
  `crypto.randomBytes`, not browser cookies, and are never read from or
  written to the real browser cookie jar.
- No outbound network requests are made to any external site.
- `/api/session/inject-demo` only accepts an id that already exists in the
  server's own `sessions` object — it cannot be used with an arbitrary or
  real-world value.
